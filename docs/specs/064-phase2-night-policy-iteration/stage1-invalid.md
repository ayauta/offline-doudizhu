## 3. 成因

**直接成因**：`benchmarks/cf-pi-stage1.test.ts` 的 `runArm` 调
`runPairTournament(..., { quiet: false })`，使每一副的累积胜负被流式打印；调用方又把
stdout 重定向到文件，于是**一个持久的、可被随时打开的中间结果文件**被造了出来。

**为什么是设计错误而不是操作失误**：no-peek 要求**在跑完之前不存在可读的中间结果**，
而不是要求「别去读它」。把中间结果写进一个日志文件，就等于把这条纪律交给在场每个人的
自制力。§14 的措辞是「不得被查看」，但一条只有在没人查看时才成立的保证，不是保证。
正确的形态是：**结果只在两臂都结束后一次性产出**，中途没有任何数字可读。

同一文件里确实有一个正例：`INVARIANT` 分支直接对局、只在结束时输出 divergence 计数，
中途不打印任何胜负数——所以它在这次事故里完全没有泄漏（0 条进度行）。差别不在运行方式，
在**是否把中间结果写出来**。

**检测缺口**：我自己的存活监视器用
`grep -E 'invariant|divergent|stage1|EXIT=|AssertionError|Error'` 过滤日志，这个模式
**不匹配**进度行的 `deal N/200 wins W/...`，所以它既没有把中间结果呈现给我，也没有在
有人打开日志时发出任何提示。监视器只回答了「还在跑吗」，没有回答「跑的过程中产生了
什么可读的东西」。

## 5. 这一轮为什么不能继续

§14 逐级停止规则把 no-peek 违规归到「任一门禁失败」一类：**允许修实现，但该池已消费的
部分不得回收；本轮不得用同一池出判定**。而 Stage 2 的前提是 Stage 1 通过，Stage 1 已经
INVALID，所以：

* 不能用 `120001–120200` 重出 Stage 1（同一池、同一轮）；
* 不能跳过 Stage 1 直接跑 `130001–131200`（§9/§11 明确要求 Stage 1 通过才跑 Stage 2）；
* 不能换 threshold / 换模型 / 换子群抢救（§13）。

要继续这条机制线，必须**开新池 + 重新预登记**（§13/§14）。

**Stage 1 没有产生任何科学结论。** 被读到的 9 副累积胜负**不构成**正、负或零的证据：
它既不是全部 200 副，也没有走完 paired 估计与 cluster 区间，更没有任何门禁被判定。
把它读成任何一种倾向都是 §14 明确禁止的「把 INCOMPLETE 解释成 KEEP / REVERT / POSITIVE /
NEGATIVE」。

## 6. 修掉的泄漏

`benchmarks/cf-pi-stage1.test.ts` 的两处 `quiet: false` 改为 `quiet: true`，
并在 `runArm` 上写明理由。**这不是调参**——它不改变任何被测量的东西（同 seeds、同 deals、
同两臂、同模型），只改变「跑的过程中磁盘上有什么可读」：

* 修改前：每跑完一副，累积胜负总数与胜率被写进 stdout；
* 修改后：**中途没有任何结果行**，两臂结束后一次性产出 dump。

同时校正了本文档之外的一条自查方式：监视器与存活检查**不得**用会把中间结果带进对话的
过滤模式去扫进度日志；需要判断存活时只数进程与行数，不读内容——本次 §2.1 的范围认定就是
这样做的（只数行，不读值）。

加了守卫（`tests/core/cf-pi-corpus-guards.test.ts`，2 条）：断言 runner 源码里
**不出现 `quiet: false`**、**出现 `quiet: true`**、且**仍然调用 `runPairTournament`**。
第三条是防「为了让守卫变绿而干脆不跑对局」——只看第一条的话，一个什么都不测的 runner
会完美通过。变异实验：把 `quiet: true` 改回 `false` → 这 2 条红，其余 27 条绿。

**同类的潜在隐患（本轮不动）**：`benchmarks/cf-gate-b.test.ts` 仍然传 `quiet: false`。
它属于已经跑完并已判定的 Gate B，其 runner 与结果都已冻结，改它属于动冻结产物；但它对
**下一次**有人重跑或照抄该文件时是同一个陷阱，记录在此。
