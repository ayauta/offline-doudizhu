## 2. 为什么没在 08:30 停：机器挂起

* `2026-09-21 03:24` 时 uptime 为 `21h58m`；现在为 `31h47m`。
  墙钟前进 **29h46m**，uptime 只前进 **9h49m** → **约 20 小时处于挂起/休眠**。
* 语料 worker 的 CPU 时间：`02:18` 为 `3617s`，`09:10` 为 `7529s` ——
  6 小时 52 分的墙钟里只累积了 **3,912 s CPU（约 15% 占空比）**。
  一个 CPU-bound worker 全速应累积约 `24,700 s`。
* 我的 liveness 监视器靠 `sleep` 轮询，机器一挂起就一起冻结，所以它们既没有报错，
  也没有在到点时提醒我。

**这是一次操作失败，不是负载估算失败。** 我被告知硬停两次，并被明确要求「到 08:30
杀掉仍在执行的 stage 并记录 INCOMPLETE」。我依赖监视器的超时事件来推进，**没有自己核对墙钟**。
监视器的 `timeout` 只保证「最多等这么久」，不保证「到点一定叫醒我」——把停表责任交给它是错的。

## 5. 教训（写给下一次用的）

1. **硬停必须由一个独立的、不看机器状态的时钟来守。** `sleep` 轮询在机器挂起时静默失效。
   正确做法是 `sleep` 之外再加一个绝对时间的检查，或者干脆把停止动作交给 `cron`/`timeout`，
   而不是交给我自己记得看表。
2. **长跑开始前要确认机器不会休眠。** 20 小时的挂起把一次 3 小时的作业变成了一次
   跨夜的失败；`systemd-inhibit` 或等价的抑制手段本该在启动时就加上。
3. **监视器的 timeout 事件不是闹钟。** 它只说明「这段时间内没有变化」。
   我把它当成了「到点会叫我」，这是本轮失败的直接原因。
4. **§14 的 no-peek 改造是对的，而且它在本轮救了场**：因为结果只在两臂结束后原子写一次，
   这次中途被杀**没有**在磁盘上留下任何可读的部分结果——否则本轮的处置会与 Spec 064 一样
   狼狈。这条纪律值得沿用到任何长跑。
