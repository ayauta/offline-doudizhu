## 1. 目标与不可越界的约束

### 目标
四个电脑档位（`casual 休闲` / `default 默认` / `expert 高手` / `master 大师`）：
1. **每档都在限定时间内给出答案**——用户已拍板：口径是**端到端 480 ms 响应窗口**（由 deadline + fallback 机制实现），worker 内 16/40/120 ms 只是内部工作预算。
2. **四档分明**——差异要能被测量出来。
3. **绝不能影响手感**。

### 硬约束（改任何行为前必读；违反会被门禁拦下）
- **不加依赖/框架/Worker 池/原生桥**；无网络、无遥测、无分析。
- `src/core` 必须是纯 TS：无 DOM、无定时器、无墙钟、无存储、无环境随机（`scripts/check-boundaries.mjs` 强制）。
- **AI 只看脱敏 `PlayerView`**；大师的「可能世界」只能由公开信息构造。**不可出千**（用户明确强调）。
- **弱档只能因为「对局面看得更简单」而弱，绝不能靠故意犯错**（Spec 051:9-12、product-spec:212-213）。随机不得直接选出更差的动作。
- 不把增强 AI 搬回主线程；新增增强策略模块必须同时加入 `scripts/ai-delivery-rules.mjs`（唯一事实源，两个门禁都从它读）。
- **机器相关的绝对墙钟时间不得成为日常硬断言**（ADR 0016）。`pnpm check` 保持快且确定。
- **任何新门禁/新测试，先证明它会在回归时变红**，再声称有效（用户反复强调的工作方式）。
- 用户可见行为一律不变：DOM 不变、**520 ms 节拍与 480 ms 窗口不变**、无 spinner、无「思考中」文案、提示即时、turn 级降级静默。
- 体积预算（硬编码在 `scripts/check-bundle.mjs`）：main JS 21001 B、CSS 5845 B、**worker 9217 B**。当前用量：19.67 KiB / 5.32 KiB / **8.16 KiB**（worker 余量约 861 B）。

pnpm check                             # 完整日常门禁

## 2. 评测基座（本阶段新建，先读这一节再动手）

### 文件
| 文件 | 作用 |
|---|---|
| `benchmarks/ai-tournament.ts` | 赛制、出厂路径包装、时钟埋点、进度与报告输出 |
| `benchmarks/ai-stats.ts` | 分位数、Wilson 区间、**按副牌聚类的 bootstrap**、所需样本量 |
| `benchmarks/ai-benchmark.test.ts` | 8 个测试：统计自检、每档延迟、逐对胜率、最宽对照、确定性/结构金丝雀 |
| `vitest.benchmark.config.ts` | 900 s 兜底超时、`fileParallelism: false`、`disableConsoleIntercept: true` |
| `tsconfig.json` | `include` 增加了 `benchmarks/**/*.ts`（此前从未被类型检查） |

### 设计要点（**别回退这些**）
1. **必须跑出厂路径**：调用真正的 `decideEnhancedAi(request, runtime)`，`ENHANCED_AI_BUDGET_MS` 从 `src/app/ai/decision-handler.ts` **import**，**绝不在基准里重打常量**。旧基座就是因为自带替身策略（大师用 `maxWorlds: 4`，而出厂是 32）而与产品脱节。
2. **零产物体积地测「截断」**：`shouldContinue` 是 play 路径上 `runtime.now()` 的唯一消费者，所以包一层 `now` 并记录「是否返回过 ≥ deadline」= 「本档自己的预算检查是否触发过」。**不要往生产代码加计数器**（`decision-handler.ts` 属于 `WORKER_REQUIRED_PATHS`，任何埋点都会进 worker 包）。
3. **赛制每局只有一个强座位**（Arm A 强坐地主 / Arm B 强坐农民，各 3 局/副）。旧赛制有 3 局是「强档占 2 个座位」，那种局几乎恒强，不携带档位质量信息。
4. **统计单位是副牌，不是局**：同副牌内决定论成立，局是聚类。用按副牌聚类的 bootstrap CI。报告 p95 需 n ≥ 200、p99 需 n ≥ 1000，否则打 `n/a`。
5. **必须活下来**：每对相邻档一个独立 `it()`；每副牌一行进度**流式**输出；`AI_BENCH_SECONDS` 软上限在开始新一副前检查，到点干净收尾并报告「已跑 X/Y 副」。旧的单 `it()` 撞上 60 s 超时后**整份报告丢失**。

### 怎么跑
```bash
# 完整基线（本阶段用的就是这条）
AI_BENCH_DEALS=400 AI_BENCH_SECONDS=300 AI_BENCH_PROBE_DEALS=40 \
AI_BENCH_CONTROL_DEALS=20 AI_BENCH_UNBOUNDED_EVERY=20 pnpm bench:ai

# 只跑一对，快速迭代（强烈建议）
AI_BENCH_PAIRS=expert:master AI_BENCH_DEALS=200 AI_BENCH_SECONDS=600 pnpm bench:ai
```

环境变量：`AI_BENCH_DEALS`(20) `AI_BENCH_SEED`(301) `AI_BENCH_SECONDS`(240) `AI_BENCH_PROBE_DEALS`(4) `AI_BENCH_CONTROL_DEALS`(10) `AI_BENCH_UNBOUNDED_EVERY`(10) `AI_BENCH_PAIRS`(all，形如 `casual:default,expert:master`) `AI_BENCH_STRICT`(0) `AI_BENCH_TRUNCATION_CEILING`(0.25)。

**耗时参考**：master 参与的对约 4 s/副（会撞软上限）；casual/default/expert 之间的对极快（15 s 能跑 700+ 副）。

### 报告里各项的含义
- `truncated` = 该档自己的预算截断了工作（≠ 玩家被降级；端到端降级是另一回事）。
- `overshootP99` = 决策实际耗时超出预算多少（轮询粒度决定，所以单次可能略微超出）。
- `headroom` = `480 / p99`，**机器相对**。性能判断一律以 **p99 + 安全系数**为准，`max` 只作记录，**不要当稳定估计量**。
- `agree` = 抽样决策在「出厂预算」与「无限预算」下命令一致的比例 → 预算吃掉了多少决策。
- `master rollout overturned the expert leader` = **大师的搜索有没有真的改变出招**，这是判断大师搜索是否在起作用的直接指标。

### 基座的可信度（已按「先证明会变红」验证过）
| 门禁 | 注入的回归 | 结果 |
|---|---|---|
| 无界轮询次数金丝雀 | `maxWorlds: 32 → 8` | ✅ 红：`expected 8 to be 32` |
| strict 截断上限 | `master` 预算 `120 → 0` | ✅ 红：`truncates 100.0% of decisions` |
| 确定性重放 | 给休闲评分注入随机 | ✅ 红：命令日志不一致 |
| 部分结果存活 | `AI_BENCH_DEALS=100000 AI_BENCH_SECONDS=15` | ✅ 干净收尾、有报告、退出 0 |

**另外修过两个基座自身的 bug**（别踩回去）：
1. 无界抽样计数器原本是「每策略实例」计数 → 没有哪个座位在一局里会做满 20 次决策，导致抽样几乎从不触发、`agree` 全是 `n/a`。现在是**按 recorder 的全局计数**。
2. 原本断言「休闲/高手在出厂与无限预算下 100% 一致」→ **高手实测有约 0.1% 的决策会被 40 ms 预算截断**，这条断言是我写错的。现在只对休闲硬断言（p99 0.55 ms vs 16 ms 预算），高手改为报告。

**可复现性已验证**：同一套种子重跑，胜率逐位相同（本阶段复跑 `expert vs default` 得到 49.6% [48.4, 50.8]，与基线完全一致）。所以前后对照可信，不需要重复跑很多遍。

## 4. 两个已做并被否决的实验

两个实验都是**先在出厂配置上量出基线 → 改一处 → 用同一套种子重跑 → 对照**。

### 实验 A：去掉「高手」对默认排序的锚定 —— ❌ 否决

**缺陷**：`defaultPolicyPrior = max(0, 12 − casualRank) × 160`（`src/core/ai/scoring-policy.ts:185-190`，在 `:228` 逐候选施加）把高手的排序锚在**默认自己的排序**上；而高手自己加的 `publicControlScore` 只有 ±210 量级。所以高手≈默认。

**改动**：移除该先验、移除由此派生的评估顺序，让高手只按自己的评估排序（默认档一行不动）。

**结果**：

| 配对 | 出厂（有锚定） | 移除锚定后 |
|---|---|---|
| default → expert | 49.6% [48.4, 50.8] | **36.8% [35.2, 38.5]** |
| casual → default | 54.8% [53.2, 56.3] | 54.8% [53.2, 56.3]（逐位相同） |
| 对照 casual → master | 53.3% | 36.7% |

`casual → default` 两跑逐位相同 → 证明改动只落在高手路径、且 36.8% 不是噪声。**移除锚定让高手大幅变弱，并把大师一起拖下水**（大师的候选名单来自高手的排序）。已回滚。

### 实验 B：把大师的 rollout 权重放大 10 倍 —— ❌ 否决

**先量出现状**：出厂配置下，大师的 rollout **只在 6.9% 的决策上推翻高手的首选**（12/174）——这就是它全部的作用，换来对高手 +3.2 个点。

**改动**：混合权重 `0.2 → 2.0`（`src/core/ai/master-policy.ts:305`）。

**结果**：

| | 出厂（0.2） | 权重 2.0 |
|---|---|---|
| rollout 推翻高手首选 | 6.9%（12/174） | **13.0%**（38/292） |
| master vs expert（合并） | 53.2% [51.1, 55.4] | **48.9% [46.3, 51.1]**（876 局） |
| 大师当地主时 | — | **42.2% [37.7, 46.8]** |
| 大师当农民时 | — | 55.5% [51.4, 59.6] |

优势直接消失，伤害集中在大师当地主时。已回滚。（诚实说明：两跑区间在 51.1% 处刚好相接，方向可信但**不算铁证**；分臂数据更清楚。要钉死的话把样本翻倍再跑一轮。）

## 5. 结论：瓶颈在哪

**两次都是「让这套评估里的某个成分说了算」，两次都变差。**

- 让高手的评估说了算 → 比默认还差。
- 让大师的 rollout 说了算 → 大师的优势消失。

所以：**瓶颈是评估项本身的质量，不是权重、也不是搜索深度。** 这套启发式评估里有一个「勉强可用」的配置（高手带锚定 + 大师小权重 rollout），但它经不起任何成分被放大。**继续拧旋钮预期是负收益。**

## 6. 没试过的方向（按「有证据支持」排序）

### 6.1 给评估项做标定（我认为唯一真正可行的路）
用可优化的目标（固定种子自对弈的胜率）去调评估项权重，而不是人肉猜。需要训练/验证划分以免过拟合到特定牌局。工作量大，但方向正确——上面两个否定实验都指向这里。

### 6.2 残局搜索（文献支持最强）
腾讯 TGDC 一手分享：模仿学习在**残局**（对手剩 1–2 张）犯系统性错误；他们的修法是「猜牌模型（134 种组合、top-3 命中 93.86%）+ minimax」，而且**朴素 minimax 一手要几十分钟，靠剪枝/缓存/节点排序拿到约 10⁶ 倍加速才降到毫秒级**。本仓库大师的 rollout 目前每 world 3 候选 × 3 层都要重跑完整 `generateLegalActions`，**开销很可能由重复的合法动作生成主导**——先量开销构成，缓存可能就能把大师从「装不下」变成「装得下还更深」。

### 6.3 两个便宜但没试过的旋钮
- **短名单 3 → 5**：Spec 051:95-96 写的是「top **three to five** actions」，实现只取了 3（下限）。这是规格允许的广度杠杆（不同于加权）。预期不高，但没试过。
- **rollout 深度 3 → 4**（规格允许 2–4）。同样受信号质量限制。

### 6.4 降档位
把四档降到三档。**但注意：这不是解决方案**——大师对休闲的对照也只有 53.3% [47.5, 59.2]，所以三档同样不分明，只是少一个含糊选项。数据支持的只有「少而含糊」vs「多而含糊」。

### 6.5 文献锚点（用于判断「多少差距才有意义」）
- **搜索开/关 ≈ 0.682（≈133 Elo）；同一评估函数纯调参 ≈ 0.515（≈10 Elo）**（RHCP vs RLCard / RHCP-v2 vs RHCP，DouZero 与 PerfectDou 论文，10000 副牌协议）。**这是最重要的锚点**：我们四档正落在「纯调参」那一档。
- 连 **341 个机器人、每天自动对局的 Botzone 天梯，三次快照都排不稳前十名**（北大天梯分析）。~10 Elo 级差距在工程上不可靠可测。
- **Stockfish 的 weakening 做法与我们相反**：MultiPV≥4 只在近似最优里选 + 一条上限被钳在一兵价值内的随机扰动（坏着被结构性排除）。**我们 Spec 051 禁止故意的错误，所以不能照抄这条最省力的杠杆**——这让我们的任务比 Stockfish 做 20 级更难。
- KDD 2020：深度受限的引擎**更弱但不会更像人类**，玩家读到的仍是「同一个 AI 的不同速度」。若想让四档读起来是四个对手，差异要落在规则集/风险偏好上。
- **诚实空白**：不存在「对手难度差的可觉察阈值（JND）」研究；不存在被验证过的目标胜率；没有一家商业游戏公布分档胜率。任何这类数字都是外推。
- 商业实现的一手证据：畅玩斗地主在 TapTap 写明「低段位用随机+不洗牌混合发牌，段位越高越弱化不洗牌」（**按段位门控 AI + 低档位偏向性发牌**）；腾讯专利是「按对局数据调整 AI 难度档位」。**「透视」（AI 看你手牌）查无实据**——我们的「只看公开信息」比行业更干净。
- 面向长辈（KAIST/JMIR 等）：长辈最常见的负面体验是**规则看不懂**，其次是反复失败；**限时让他们紧张**；建议是可难度、失败后提示、取消时间限制。商业数据：**70–80% 的玩家只玩最简单的档**。

### 6.6 明确不要做的
- **不要做「无敌 AI」**：腾讯自己的说法是 100% 正确没有产品价值。
- **不要靠故意犯错/放水拉开差距**：玩家感知研究一致显示「势均力敌最好、被制造的胜利最差」。
- **不要用 Elo 做验收**：正式结论一律用聚类胜率与 CI。

## 7. 踩过的坑（省你时间）

1. **`pnpm bench:ai` 的 `--testTimeout` CLI 覆盖不生效**：我试过 `pnpm bench:ai -- --testTimeout=900000`，进程仍按 60 s 计时（因为同步循环无法被中断，它会跑完并把报告打出来，然后仍被记为失败）。**改超时请改 `vitest.benchmark.config.ts`**，并且靠 `AI_BENCH_SECONDS` 软上限而不是靠超时。
2. **Playwright 的 `page.route` 拦截不到 Dedicated Worker 的脚本请求**，必须用 `context.route`（上一阶段的坑，做浏览器故障注入时会遇到）。
3. **「从未发生过」这类负向属性不能用快照断言**：要用 MutationObserver 全程观察。
4. **TypeScript 是 7.0.2 原生编译器**，没有 `ts.createSourceFile`；AST 相关 API 在 `unstable` 下且要起 Go 进程。
5. **`verbatimModuleSyntax: true`**：`import type { X }` 会被完全擦除，但 **`import { type X }` 仍会求值模块**（产物是 `import {} from "m"`），是真实的运行时边——会改变 worker 体积。
6. **改一个档就要重跑同一套种子做前后对照**，并且**先证明新门禁会在回归时变红**。
